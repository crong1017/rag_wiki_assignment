W01

RAG 的定義與目標

RAG（Retrieval-Augmented Generation，檢索增強生成）是結合「找資料」與「文字生成」的架構。先從外部知識庫找到相關內容，再讓 LLM 使用這些內容回答。

  • RAG 的重點是為生成流程提供額外上下文，而不是重新訓練模型。
  • Retrieval 找資料；Augmentation 把資料放入提示；Generation 產生回答。
  • 合適的場景包括需要特定領域或經常更新的資料。

例子：詢問「新版實驗室安全規範有哪些？」時，系統先查最新公告，然後整理為易讀答案。

W02

為什麼不能只靠 LLM？

一般 LLM 的訓練知識有時間和範圍限制，可能不知道某間組織的私有文件，也可能生成不精確的陳述。

  • 模型內部知識未必包含最新規定或企業內部文件。
  • 回答流暢不代表有證據支持。
  • RAG 提供可指定的外部資料，有助改善相關性並支持來源追溯。

例子：單靠模型可能不知道今天更新的借書規則；若知識庫已收錄新版規則，就可以先查再答。

W03

資料 ingest：蒐集、切塊、索引

將資料納入知識庫前，先確認來源可靠、文字可讀、內容去重，再依段落或主題切成適當大小的 chunks，為後續檢索建立索引。

  • Ingest 是將外部材料整理成可查詢內容的過程。
  • Chunking 可讓檢索以較小的語意單位進行，但切得過小可能破壞上下文。
  • 索引可以採關鍵字、語意或向量等方式，不是每種 RAG 都必須用向量資料庫。

例子：將一份 60 頁的工作手冊拆成「休假規則」「報銷流程」等可引用段落。

W04

Embedding 與檢索方式

Embedding 是將文字或其他內容轉成數值表徵；向量檢索比較語意相近程度，和單純比對字面關鍵字不同。

  • 向量檢索可找出不同字詞但意思接近的資料。
  • 關鍵字檢索對專有名詞、代碼或精確名稱仍有用。
  • 混合式檢索可以結合不同方式；排序不佳時可考慮 reranking。

例子：查詢「請假要先告訴誰？」也可能找到標題為「缺勤通報流程」的文件。

W05

RAG 三階段的運作流程

使用者提問 → Retriever 從索引取得相關內容 → 把提問與內容整合成 prompt → LLM 生成有依據的回答。

  • Retrieve：根據問題查找候選片段。
  • Augment：將有用片段與原始問題一起提供模型。
  • Generate：生成回答，必要時附上可回查的資料來源。

例子：問「實驗室可以飲食嗎？」→ 找出安全規範段落 → 在回應中解釋規定並顯示來源。

W06

RAG 的好處、限制與驗證

RAG 可能提升專業問題回答的相關性與可追溯性，但前提是來源、檢索、上下文與生成都足夠可靠。

  • 如果原始文件錯誤或過時，答案可能跟著出錯。
  • 如果沒找到相關片段，不應勉強生成肯定答案。
  • 需檢查來源對應、內容是否超出證據、使用者是否真的能理解。

例子：找不到更新後的政策時，應回報「目前知識庫沒有足夠資料」，而不是亂猜。

W07

RAG、Fine-tuning 與應用

RAG 用外部檢索內容補強特定知識；微調（Fine-tuning）通常透過訓練調整模型在特定任務中的行為。兩者可搭配使用。

  • 需要快速更新規定／引用來源：優先考慮 RAG。
  • 需要固定寫作格式或任務行為：可以評估微調等方法。
  • 常見應用包括內部文件問答、客服知識查詢與專業資料助手。

例子：圖書館問答系統引用最新借閱規則回答，而不是要重新訓練整個語言模型。
