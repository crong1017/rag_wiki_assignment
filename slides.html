01｜問題與目標WHY · 03/22

回答很流暢，也可能沒有依據

💬

只有模型既有知識

模型可能不知道機構內部的文件、尚未納入訓練的規定或新發布的資訊。

使用者：「昨天更新的借書規則是什麼？」
📑

先連結可查證資料

把最新版文件作為外部證據，先找到相關段落，再讓模型根據內容整理。

使用者 → 查閱文件 → 整理回答與來源
請記住：回答「聽起來合理」不等於「能從文件找到證據」。

小情境：問一個模型不一定知道的問題

🙋「我們學校最新的實驗室安全規定，是否允許飲食？」
直接回答

02｜核心觀念DEFINITION · 05/22

RAG 到底是什麼？

Retrieval＋Augmented＋Generation
R

檢索

找出與問題最相關的文件片段

A

增補

將片段連同問題放入提示脈絡

G

生成

由 LLM 產生能回查證據的回覆

RAG 是組合檢索與生成的應用架構，並不等於模型重新訓練。

02｜核心觀念TWO PIPELINES · 07/22

RAG 其實有兩條流程

A離線準備（建資料庫）
蒐集資料→切塊與清理→建立索引

可以在資料更新時重新執行，不必每個問題都重新 ingest。

B線上問答（有人提問時）
輸入問題→檢索片段→LLM 回答

每一次提問通常都會重新檢索，而不是每次重建整份知識庫。

索引是兩條流程之間的橋樑：先準備知識，再讓查詢使用它。

Ingest：先把資料變成可查的知識

①蒐集網頁／PDF／文件
→
②清理可讀、去重、正確版本
→
③切塊保留語意與章節

03｜檢索技術RETRIEVAL · 11/22

關鍵字、向量、混合檢索有什麼差別？

Keyword Search

比對字面

精確型號、代碼、文件名稱通常很適合。

例：搜尋 LAB-2026-A
Vector Search

比對語意

能用不同措辭找到意義接近的段落。

例：「請假」≒「缺勤通報」
Hybrid Search

結合兩者

兼顧關鍵字精準性與語意召回。

例：代碼＋自然語言提問
不是所有 RAG 都必須使用向量資料庫，選擇方式取決於資料與查詢需求。

03｜檢索技術FULL JOURNEY · 14/22

從提問到答案：完整走一次

1事先整理資料可信文件 → 清理 → chunks → 索引
2使用者提問「借閱續借規則？」
3查索引與選片段取得相關證據，排除無關內容
4組提示並生成問題＋證據＋回答規則
5檢查與輸出與來源一致？必要時重新檢索
這就是完整的「資料準備 → 檢索 → 增補 → 生成 → 檢查」鏈。

04｜案例與比較COMPARE · 17/22

有 RAG 與沒有 RAG，差在哪？

WITHOUT RETRIEVAL

只看模型已知資訊

  • 對最新或內部文件可能不清楚
  • 回答可能缺少可查證依據
  • 不容易知道依照哪一份規定
WITH RAG

先查文件，再生成

  • 能使用已更新且有權限的資料
  • 可設計來源引用與回查連結
  • 仍需檢查來源正確、檢索正確
RAG 的優勢是「能利用外部證據」，不是「保證永遠正確」。

RAG 跟 Fine-tuning 是同一件事嗎？

📚

RAG

查閱外部文件，把相關內容放入模型輸入。

適合：常更新的文件、需要引用
⚙️

Fine-tuning

透過額外訓練調整模型對特定任務的行為。

適合：任務格式、風格或行為調整
兩者可以互補；本次作業建立的是知識整理與 HTML 教材流程，沒有進行模型微調。

05｜驗證與複習QUALITY · 19/22

RAG 最容易在哪三個環節出錯？

01 · SOURCE

文件錯 / 過期

原始資料本身不可靠，即使檢索正確也可能答錯。

檢查：版本、來源、日期
02 · RETRIEVE

找錯 / 漏找片段

檢索結果與提問不相關，後續上下文就失焦。

檢查：相關性、覆蓋率
03 · GENERATE

誤讀 / 過度延伸

模型回答超出找到的證據，即使附引用也可能不準確。

檢查：逐句對照來源
真正的品質控管：資料、檢索、答案三段都要檢查。
